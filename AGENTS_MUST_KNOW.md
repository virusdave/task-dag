# AGENTS_MUST_KNOW

Read and follow this file before doing Sweed work in this directory.

## Critical Rules

- Never implement a quadratic-or-worse approach without explicit user approval. This applies to code, SQL, and mixed workflows together. Always reason about the holistic runtime of the full implementation, not just one local step. Default to designs that are `O(N log N)` or better unless the user explicitly approves a slower approach.
- UI labels are often not API values. Many Sweed fields are typeahead selectors that submit internal IDs such as `sizeId`, `strainId`, `categoryId`, `subcategoryId`, and `distributorId`.
- Sweed's help-center `product` maps more closely to our RPC `product group`, and its help-center `variant` maps more closely to the sellable RPC `product` row created by `store.product.add`. Keep that translation straight when designing catalog migrations or interpreting UI docs.
- Product type and subcategory are not interchangeable. Help-center docs say product type is customer-visible and reusable across categories, while subcategory is single-category taxonomy and not the main customer-facing differentiator. Use product type for visible distinctions like `buds`, `littles`, or `shake` instead of stuffing those differences into names or one-off subcategories.
- Live `store.product.category.list` can expose disabled subcategories with `enabled: false`, and old groups can still remain attached to them. Treat those disabled subcategories as invalid for every new create/apply flow: never attach them, and if a live group is still using one, clear it on the product group with `store.product.group.edit { id, subcategoryId: null }` unless a reviewed enabled replacement is explicitly approved.
- For catalog-family migration, do not auto-merge same brand/category/name groups before classifying the lane. The live catalog still has many null-subcategory `Pre-Rolls` and `Vapes`, so collapsing same-name families too early can merge infused vs plain pre-rolls or cartridge vs disposable vape rows incorrectly.
- For null-subcategory preroll lane inference, do not trust full-description keyword scans by themselves. The generated marketing copy can mention sibling infused formats even when the current group is a plain pre-roll, so safer lane evidence comes from names, variant names, and only the opening description text.
- Same-name duplicate groups can carry different family metadata. When consolidating families, choose the canonical group deliberately so the surviving row keeps the best strain, description, and image payload before variants or distributor links are moved.
- Review labels for strain prevalence may also need aliasing before live writes. On 2026-04-12, the live prevalence dictionary had `Hybrid`, `Indica Dominant`, `Indica`, `Sativa Dominant`, and `Sativa`, but not `Indica Hybrid`, so that review label had to be mapped to `Indica Dominant`.
- Live `store.product.strain.add` validation in this workspace requires `prevalenceId`. On 2026-04-13, name-only strain-create attempts failed with `Parameters validation error` / `Required properties ["prevalenceId"] are not present`, so approval-locked exact-strain creates with blank prevalence need an explicit execution-time prevalence decision instead of assuming Sweed will accept a bare exact strain name.
- Product catalog work usually happens at the state level. Inventory and purchase work usually happens at the site level.
- Never assume a live session is still at the correct dealer or level from an earlier step. At the start of each programmatic operation block, explicitly call `store.auth.dealer.set` for the intended context and verify the returned `currentDealerId` / `currentDealerName` before doing reads or writes.
- If a live site-scoped read suddenly fails with an unexpected API response or a previously visible site-owned object looks unreadable, first recovery step is to call `store.auth.dealer.set` again for the intended dealer and retry the site-scoped read a few times. In this workspace the session can be shared across agents or the user, so dealer context can drift between adjacent calls.
- Wrong-level calls can fail in misleading ways. On 2026-04-11, purchase order `108224` returned `PurchaseOrder not Found` from `store.purchase.order.get` until the session was switched back to the Midtown site dealer `210705`, and `store.distributor.product.suggestion` from the wrong level returned an empty `orderPositions` array for the same live order.
- If catalog edit calls like `store.product.group.edit` or `store.product.edit` fail with a misleading "not found or you do not have permission" error while read calls still work, verify the session is operating at the state-level catalog context rather than a site-level context.
- Keep `/Users/dave/tmp/scratch/fbnyc/sweed/catalog/AGENT_TODO.md` current whenever the active queue, generated artifacts, progress, blockers, or next steps materially change. Treat this as a standing instruction for interrupted-work handoff, not a one-off reminder.
- Always keep the workspace knowledgebase up to date when you learn something durable. Write the finding into the smallest correct canonical doc immediately, then update the nearest index file so another agent can find it with an index-first path instead of rediscovering it from threads, handoff notes, or code archaeology.
- Keep knowledgebase organization optimized for fast agent lookup and low-context reads: prefer a shallow index -> subsystem doc -> task doc hierarchy, put rules near the workflow they govern, and avoid burying important guidance only inside large narrative files or stale handoff logs. Use `HOW_KNOWLEDGEBASE_WORKS.md` when you need the canonical layout and maintenance rules for the docs system itself.
- On this nix-darwin host, direct Playwright browser launches have repeatedly failed with `SIGTRAP` across nixpkgs browser bundles, Playwright-downloaded Chromium, and local Chrome. For browser automation or screenshots here, prefer the Dockerized official Playwright image workflow documented in `HOW_PLAYWRIGHT_WORKS.md` and `docs/playwright/` unless you have a fresh verified host-level fix.
- For one-off tooling invocations (imagemagick, jq, ffmpeg, ripgrep extras, csv/yaml utilities, etc.), strongly prefer `nix-shell -p <pkg> --run "<cmd>"` over spinning up a Docker container. Docker is heavyweight, slow to start, and pollutes the system; nix-shell is fast, hermetic, and self-cleans. Use Docker only when nix-shell genuinely cannot satisfy the requirement (Playwright on this nix-darwin host is the canonical example documented above; another would be a tool that ships only as an opaque container image with no nixpkgs derivation).
- Before using any LLM in this workspace - Amp built-ins like Oracle or Painter, private remote backends like Bedrock Mantle, local LibreChat surfaces, or a newly proposed model/backend - consult `HOW_PRIVATE_LLM_ACCESS_WORKS.md` and `config/llm_use/registry.yaml` first.
- If the intended LLM/backend/use-case combination is not already listed as approved or explicitly limited-trial in `config/llm_use/registry.yaml`, record it there before proceeding and keep the first use bounded to the named trial scope.
- To enumerate the current outstanding purchase-order queue for this project, use the site-level purchase list call `store.purchase.order.list` with a delivery-date window and `orderStatusId: 2`. The 2026-04-11 HAR captured `store.purchase.order.list { orderStatusId: 2, fromDate: "2026-04-01", toDate: "2026-10-11", page: 1, pageSize: 50 }`, which returned the outstanding delivered orders for the active site context.
- Distributor display names are not unique. `HR BOTANICAL DISTRIBUTION LLC` was observed with at least two different Sweed distributor IDs.
- `store.product.group.list` is not a safe uniqueness key for duplicate checks. The same normalized Hepworth product-group name can exist under multiple group IDs, so check duplicates against `store.product.list.short` at the variant level before creating anything new.
- If the exact variant already exists, prefer creating only the missing `store.distributor.product.add` link for the correct distributor instead of creating a duplicate product group or variant.
- `store.distributor.product.suggestion` can return `orderPositions[]` rows even when a usable catalog candidate already exists. Treat empty `products[]` arrays as the real "no current suggestion" case; populated `products[]` means the remaining work is purchase-side mapping, not another catalog-create pass.
- `store.distributor.product.suggestion` is not a complete unresolved-line inventory when a purchase row is already attached to a generic placeholder product. On 2026-04-14, Midtown order `108920` position `668221` (`Sushi Hash Hash-Hole 1g Single Charmz x Jelly Roller Rosin (S)`) was still effectively unmapped even though the PO carried distributor product `390788 -> product 240706 Preroll Samples Samples`; the suggestion endpoint omitted that position entirely. The same omission pattern recurred on 2026-04-22 for Midtown Hemp Hunter Labs Camino fruit-chew rows whose current mapped product was `Edibles Samples 10x 10mg`. Proposal scans must treat those known generic placeholder mappings as unresolved and recover them from `store.purchase.order.get().positions[]` when the suggestion payload skips them.
- Some integration-owned distributor-product rows cannot be repointed with `store.distributor.product.edit`. On 2026-04-11, distributor product `538185` returned `Forbidden to change distributor product created through external integration`, so the safe fallback was to create a separate linked `store.distributor.product.add` row for the same external name and distributor.
- The same practical fallback applies when Sweed returns the plainer `Forbidden to change distributor product` error. On 2026-04-14, Bronx Capital Region row `545047` rejected `store.distributor.product.edit { id: 545047, productId: 384378 }` with subcode `713`, so a separate linked distributor-product row remained the safe path.
- The product name shown to users is often programmatically constructed from component parts. Do not assume a raw purchase or distributor item name should be copied directly into the catalog.
- Public-facing product and group names should not keep strain/prevalence suffixes as literal name text. Strip trailing labels and malformed fragments such as `(Indica)`, `(Sativ`, or `| Hybrid` from catalog names and keep that information on the actual strain/prevalence fields instead.
- Renaming a product group with `store.product.group.edit { name }` does not automatically rename existing variants. If the approved public-facing variant name must change, follow with `store.product.edit { name, shortName }` on the product itself.
- Multi-unit variant naming is a state-level catalog rule, not just a pre-roll import convention. For any variant with `packOfSize > 1`, the canonical naming pattern is `${QTY}x ${UNITSIZE}` such as `10x 0.35g` or `2x 1.5g`, and the live fix belongs on the product variant through `store.product.edit` from the state dealer context.
- Never use em dashes in product descriptions. Use plain hyphens, commas, or separate sentences instead.
- Before scripting create calls, resolve labels like brand, category, subcategory, strain, size, sale type, and distributor to their internal IDs.
- When resolving subcategories for live create/apply work, filter the category's subcategory list to `enabled: true` rows before choosing a `subcategoryId`. Disabled historical lanes like `Chews/Gummies`, `Drinks`, `Pre-Packaged Flower`, and old accessory buckets must stay unattached.
- Catalog attribute backfills such as strain, effects, flavorings, and scents belong on the product group, not the variant. Use `store.product.group.get` / `store.product.group.edit` for attachment, and use separate nomenclature APIs like `store.product.strain.*` to create or resolve the underlying dictionary records first.
- For live preroll subcategory migrations, edit the product group, not just the variant. On 2026-04-13, `store.product.edit { subcategoryId: ... }` only changed the product-level override, while `store.product.list.short` and ecommerce-visible preroll subcategories continued to follow `store.product.group.get().subcategory` until `store.product.group.edit { id, subcategoryId }` was applied.
- After preroll group subcategory edits, `store.product.list.short` can show stale subcategory values unless the request includes `reload: true`; `store.product.group.get` also reflected the new group subcategory reliably during verification.
- After live `store.product.edit` writes on existing variants, `store.product.list.short` can update the row name while still serving stale numeric fields such as `packOfSize: 0` and `price: 0` for that same row, even with `reload: true`. `store.product.get` can also lag briefly behind `store.product.group.get().products[]`, so immediate post-write verification should prefer the group payload first, then retry the direct product read before treating the edit as failed.
- For the all-in-stock catalog update pass, use the site-level in-stock report only to define scope. Collapse the variant-level report/export to unique `groupId` actions, then perform every catalog write from the state-level catalog context.
- For online-availability audits, `store.inventory.item.list.grouped` is the key site-level report. The grouped row totals are not enough by themselves; inspect each entry in `items[]`, which was observed to carry `stockLocation`, `isTradeSample`, `isAvailableOnline`, and per-item quantity fields.
- Only auto-apply rows whose in-stock analysis status is already strong enough for writes: `reviewed-group`, `verified-proxy`, or `verified-equivalent`. Leave `inferred-candidate` and `generic-or-missing` rows unchanged unless they receive further review, and skip rows whose recommendation is effectively `No strain action`.
- Do not use category flags or category names alone to prune catalog-attribute review. In the 2026-04-11 in-stock analysis, some edible rows still carried specific strain context worth preserving or reviewing, so treat category capability flags as hints rather than a sole gate.
- If direct Sweed RPC reads suddenly start returning a Cloudflare challenge page or HTTP 403 in this workspace, try forcing IPv4 before assuming the auth token or payload is wrong. Identical calls have succeeded over IPv4 after failing over the IPv6 path.
- For purchase-order costing, prefer the live Metrc field `positions[].orderPositionIntegrationData.wholesalePrice` when the purchase payload exposes it. It is an extended line amount, so divide by the position quantity to get the unit cost. If the field is absent, treat the PO-side Metrc unit cost as unknown rather than silently forcing `0.00`.
- For the combined outstanding-PO packet, missing live PO wholesale is a costing gap, not a scope filter. Keep every non-definitively-mapped purchase line in the combined packet even when `orderPositionIntegrationData.wholesalePrice` is absent, and only leave cost unresolved unless a confirmed manual override or reusable linked distributor price exists.
- For long-running tasks, use `page-dave` as soon as the work is ready for review or fully complete instead of waiting silently at the end.
- For generated local HTML review artifacts, always use relative references between packet files, detail pages, and sibling assets. Never emit absolute filesystem paths or `file://` links inside the generated HTML.
- For any reviewer-facing or customer-facing creative proposal in this workspace - banners, ads, promos, or other user-facing imagery - the deliverable must be an actual generated image from an approved image-generating LLM path. Do not substitute SVG/HTML/CSS compositions, vector approximations, or rasterized mockups as if they were proposal-ready creative. Those stand-ins are only acceptable to illustrate concepts when the user explicitly approves that fallback in advance, and they must be labeled concept-only rather than proposal-ready.
- When the user explicitly authorizes the `painter` tool for reviewer-ready banner/ad/promo imagery, treat `painter` as the approved default generation path in this workspace instead of inventing another image workflow.
- When the user provides specific logos, storefronts, pack shots, or other brand assets for reviewer-ready banner/ad/promo imagery, the final visible output must clearly include those provided assets. Do not treat them as loose inspiration only.
- For the private Bedrock Mantle LLM used in this workspace, keep the bearer token only in local secret storage such as `~/.secret/bedrock/mantle-bearer-token` with an optional local export helper at `~/.secret/bedrock/mantle-bearer-token.env`. Never persist the token into repo files or generated artifacts.

Source that helper before running local tools such as LibreChat against Mantle instead of copying the token into repo config.

## Critical Purchase Mapping Insight

- A purchase line can have a `distributorProduct` but no `suggestedProduct`.
- In that state, the line is effectively unmapped and may require creating the product group, variant, and distributor product.
- Creating those records can be enough for `store.distributor.product.suggestion` to start returning a usable match for the purchase line.
- Creating the exact catalog row is not guaranteed to make `store.distributor.product.suggestion` start proposing matches. On order `108224`, the exact `Old Pal Blueberry OG 3.5g` and `Old Pal Cherry Durban 3.5g` catalog rows were created successfully, but the site-level suggestion response still returned `orderPositions[].products: []` for all four positions until any purchase-side mapping step.
- A purchase line can also already carry a current-distributor `distributorProduct.id` but still be unmapped to any catalog product. On order `108216`, the unmapped Ayrloom sample lines already had distributor-product records `537911`, `537912`, and `537913` on distributor `4242`.
- When the exact variant already exists and the PO already carries a current distributor-product record, the safer remediation is likely to map that existing distributor product onto the existing variant rather than create another `store.distributor.product.add` row.
- In that state there may be no remaining catalog-side write at all. If the reusable variant already exists and the user intends to handle the purchase-side mapping manually, stop at review artifacts and do not force a catalog mutation.
- We have not yet captured the API that explicitly assigns a suggested product to a purchase position.

## Critical Pricing Heuristic

- Use the post-tax GM% formula in this workspace: `GM% = 1 - 1.13 * cost / price`.
- Target roughly 55% to 65% margin for draft catalog pricing.
- For nearby competitor pricing from the Lit Alerts provider (`public-api.litalerts.com/Products/menulistings`), do not trust the response `total` field by itself. On 2026-04-12 it stayed at `10000` while pagination continued through `13371` rows, so keep paging until you hit an empty page or a short final page.
- Treat the captured `Average Competitor Price` as a pre-tax market average. Convert it to a post-tax competitor equivalent with `1.13 * average_competitor_price`, then aim to land a few percent below that figure rather than matching it, as long as the result still stays inside the 55% to 65% GM band.
- If the current cost and competitor average make those rules incompatible, it is acceptable to propose the below-competitor price even when that drops GM below 55%. Do not go below 55% for any other reason.
- Do not leave sample rows unpriced just because their cost is nominal. If a sample line lacks a paid companion cost, still emit a price using the best available cost basis, even if that yields a near-100% GM.
- Keep categorically equivalent items by brand with the same cost and size at the same outgoing price.
- Set `global_price` only on even quarter increments: `.00`, `.25`, `.50`, or `.75`.
- Prefer `.00` and `.50` endings over `.25` and `.75` whenever that still satisfies the active pricing constraints.
- Do not use charm pricing such as `x.99` or similar non-quarter endings.
- When Lit Alerts product identity is ambiguous, use the state-wide brand lookup flow instead of guessing from menu text alone: first resolve the brand ID with `GET /Manufacturers/real?page=0&pagesize=2000&state=NY`, then query `POST /Products/menulistings` with `brandIDs: [id]`, `filters.Brand: "[id]"`, `dispensaryIDs: null`, and `stateID: 265` to inspect the brand's statewide listing set. In that mode, do not trust the response `count` field as the listing count; use `listings[]` and `total`.
- For Lit Alerts product matching, discovery should be broader than pricing comps: keep the brand and category anchored, but use a short durable family token in `filters.Name` and read the statewide retailer-listing cluster as a whole instead of requiring exact menu-name equality. Preserve strict same-brand, same-format filtering only after identity is established. See `docs/litalerts/product-matching.md` via the `HOW_LITALERTS_PRODUCT_MATCHING_WORKS.md` index.
- Lit Alerts `filters.Name` search appears to behave like an exact substring match rather than a fuzzy token bag. For statewide identity discovery, pick the rarest contiguous 1-3 word phrase from the actual product text, then pair it with the resolved brand ID and category filter instead of sending a long normalized pseudo-name.
