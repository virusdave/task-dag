Live runs now correctly report Bronx 1226 variants / 148 in stock and Midtown 323 variants / 259 in stock.
- The Postgres "inconsistent types deduced for parameter $6" failure on the `stock_variant_state` upsert is also fixed by casting `$6` to `timestamptz` so the conditional `case when $3 then $6 else null end` branches resolve to a single concrete type.

### Oracle-Reviewed Implementation Path

- Treat Helios as a modular monolith, not a fresh rewrite and not a plugin-heavy platform.
- Keep one Fastify app, one React shell, one auth/session layer, one job queue + worker, one audit stream, and one dependency-health model.
- Make `catalog` the first Helios module, then migrate other workflows under `/internal/tools/<module>` instead of keeping them as separate apps.
- Migrate new workflows by wrapping existing scripts as typed worker-job adapters first; only move logic into shared libraries after the workflow shape is proven.

### Recommended Delivery Phases

- Phase 1: add `APP_BASE_PATH` support and make server routes, static hosting, client routing, fetch paths, and auth redirects safe under `/internal/tools`.
- Phase 2: add a lightweight module registry and Helios shell so catalog becomes module one and future modules can register routes/navigation cleanly.
- Phase 3: generalize shared job, audit, and dependency patterns before landing the second module.
- Phase 4: migrate `screens` first as the pilot non-catalog module because it best matches the existing dry-run, review, apply, and audit workflow shape.
- Phase 5: migrate bulk utilities and pricing helpers, then CRM/segmentation, then communications.

### Consolidation Workstreams

- Catalog operations: keep the current review, catalog, history, and reconcile flows as the first Helios module.
- Screens and banner operations: fold in the `automation/screens/` workflows as a dedicated module with dry-run and live-apply affordances.
- Customer segmentation and CRM sync: fold in `automation/customers/segmentation/` with explicit job history, data-source provenance, and output review pages.
- Communications tooling: fold in `automation/communications/` with reusable templates, review artifacts, and approval state.
- Purchase, pricing, and bulk catalog utilities: expose the highest-frequency automation flows behind typed job entrypoints instead of standalone scripts.

### Architecture Direction

- Keep one shared auth/session layer, one audit/event model, and one jobs/runtime model across all Helios modules.
- Prefer module-specific pages over separate apps when the workflows share operators, audit requirements, and data dependencies.
- Preserve script-level implementations as adapters at first; move logic into shared server or worker modules only after the Helios workflow shape is stable.
- Standardize dependency health reporting so Helios shows Google OAuth, Sweed, TigerData, Lit Alerts, and Bedrock readiness in one place.
- Replace catalog-specific shared metadata in cross-module contracts before the second module lands. In particular, evolve job-linked references away from catalog-only nullable fields and toward generic linked-entity references.
- Add module-aware audit/event conventions so global jobs and audit pages can filter by `catalog`, `screens`, `crm`, `communications`, `pricing`, and `utilities` without bespoke logic.

### Guardrails And Risks

- Keep every new route, asset reference, auth redirect, and fetch path mounted-path-safe under `/internal/tools`; do not reintroduce root-relative assumptions.
- Do not let shared job or audit schemas accumulate per-module nullable fields; generalize the shape once before adding the second module.
- Every migrated live-operation workflow should keep explicit dry-run, explicit live-apply, job history, audit events, dependency gating, and operator-visible outputs.
- Keep one queue for now and use namespaced job types plus concurrency keys before considering separate workers or service extraction.
